02 Asset Pipeline

Creating a Pod

A Pod is defined once as a Data Table row, becomes a runtime UPodItem when given to the player, and — when equipped into the Shell's Pod Array — spawns its APodActor to apply effects. Here is the full path, field by field.

Part A · The Data Table row

Pods live in a Data Table built on the _PodDataTableRow row structure (C++ F_PodDataTableRow). Each row is one pod definition.

  1. Open (or create) the Pod Data Table

    Use the existing Pod Data Table asset. To make a new one: Miscellaneous → Data Table, and pick _PodDataTableRow as the Row Structure. A table's structure is fixed once chosen.

  2. Add a row

    Click Add (＋) and give the row a unique Row Name — this is the key you pass to AddItemFromDataTable, so keep it stable and descriptive (e.g. Pod_NoFallDamage_L1).

  3. Fill in the fields

    Work down the field reference below. At minimum a working pod needs an ItemName, a DisplayName, a Shape, at least one icon, and a PodClass so it can spawn its actor when equipped.

  4. Save

    Save the Data Table asset. The row is now referenceable by its Row Name anywhere in Blueprints.

Part B · Handling the Pod in Blueprints

The row is data; the behavior lives in the Pod Actor Blueprint and the way you hand the pod to the player. This is the same for every pod.

  1. Create the Pod Actor Blueprint

    New Blueprint Class → parent APodActor. The C++ base ships with no components — just the two effect events — so the root and every visual are added here in the Blueprint.

  2. Add the Static Mesh(es) & visual components

    Give the Blueprint a root Scene Component, then add the pod's geometry as child Static Mesh Components under it. Add any other visuals — extra meshes, Niagara / particles, lights, a World Crosshair — as further children.

    Build them to match how the Shell mounts the pod, or they'll sit wrong on the array:

    • Anchor on the root. The Shell attaches the whole actor to the Pod Array socket with SnapToTargetNotIncludingScale, so position meshes relative to the root — the root pivot is what lands on the socket.
    • Size on the child meshes, not the actor. On equip the Shell overwrites the actor's scale uniformly with PodMeshScale. Any per-mesh sizing must live on the Static Mesh Components; root/actor scale is discarded.
    • Leave root rotation neutral. Equip and in-grid rotation drive the actor's yaw (CurrentRotation × 90°). Bake no yaw into the root, or rotated placements double up.

  3. Implement the effect events

    Override the two BlueprintImplementableEvents on APodActor:

    • OnPodEquipped(OwnerCharacter) — apply the pod's effect (buff stats, enable a crosshair, grant an ability).
    • OnPodUnequipped(OwnerCharacter) — undo exactly what OnPodEquipped did.

    Keep them symmetric so equipping and unequipping always cancel out.

  4. Wire the Blueprint back to the row

    Set this Blueprint as the row's PodClass. When the pod is equipped into the Pod Array, ShellActor spawns it at the matching shell socket and calls OnPodEquipped; removal calls OnPodUnequipped.

  5. Give the pod to the player

    Build the runtime UPodItem from the row using the Inventory Component. Pick whichever entry point fits:

    • AddItemFromDataTable(DataTable, RowName) — the core call; returns an E_InventoryResult.
    • TryAddItemByRowName(DataTable, RowName) — boolean convenience wrapper.
    • Place an ItemPickup actor in the level with its ItemDataTable + ItemRowName set — walking over it calls the same add path.
    • A crafting recipe whose ResultPodRow points at the row (CraftPod).

  6. Let the player equip it

    In Edit Mode (shell worn, array editable) the player drags the pod from the Field Cache into the Pod Array. That fires OnItemEquipped, which the Shell listens for — no extra code needed per pod. Effects run until the pod is removed.

Watch

Don't nest scene components inside a BP-added Actor Component. For world visuals like a crosshair, keep the mesh as its own component on the actor and hold a transient, Blueprint-assigned reference to it; tune its small offsets in the Blueprint rather than adding new C++ properties. Nesting a scene component in an addable Actor Component leads to archetype/reference breakage.

Naming

Pod Array = the Shell grid of equipped pods. Field Cache = the field-item inventory. Edit Mode = shell worn, array editable. "Terminal" refers to the device only — use the Field Terminal for the dashboard UI.

Special behaviors

Core pods

A pod with bIsCoreSlot = true is equipped through the dedicated Core slot rather than the Pod Array grid, via EquipCorePod(CorePod). The Inventory Component tracks a DefaultCorePod, built from the State row (_PodDataTableRow handle) at initialization. Equipping fires OnCorePodChanged.

Unique-equip pods

Set bUniqueEquip = true to allow only one of a type in the Pod Array. Grouping is by PodTypeID when set (so a Level 1 and Level 3 of the same family still conflict), otherwise by PodClass. When a duplicate is blocked, FindConflictingUniquePod returns the offender and the component broadcasts OnDuplicatePodBlocked(BlockingPod) for the UI to flash.

Watch

The block event must actually broadcast. When a unique-equip conflict is detected, OnDuplicatePodBlocked has to fire so the UI can react — the conflict flash and the identifying BlockingPod depend on it.

Black Box pods

A pod with bIsBlackBox = true protects the first PodLevel slots of the Field Cache (slots 0 … PodLevel-1) from ClearFieldCache() while it is equipped. Because protection is keyed on PodLevel, Black Box pods are a natural fit for PodTypeID-based unique-equip so different levels of the box lock each other out.

03 Extending

Adding more asset types

Pods are the first pipeline documented here. Every other ArcDROP asset follows the same three-beat shape — use it as the template for the next entry.

1 · Data / definition 2 · Blueprint behavior 3 · Runtime handling

For each new asset, answer the same questions in order: Where is it authored (which Data Table / row struct, and what does each field mean)? What Blueprint carries its behavior (parent class, key events)? How does it reach the player (which functions or actors give it, and how is it used)?
